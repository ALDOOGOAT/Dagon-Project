================================================================================
  1. VISIÓN GENERAL DEL SISTEMA
================================================================================

Dagon es un LMS (Learning Management System) gamificado para aprender SQL/PostgreSQL.
Estética "Abyss & Crimson" (oscuro, glassmorphism, pulpo rojo).

  USUARIO → Frontend (React) → Backend (Spring Boot) → PostgreSQL
                       ↓
                  Clawbot IA (Gemini) ────→ Microservicio MPI (Analytics)

  MÓDULOS:
  - Registro/Login con JWT
  - 5 niveles progresivos de SQL (SELECT, WHERE, JOIN, GROUP BY, DDL)
  - Tutor IA (Clawbot) con retroalimentación socrática
  - Leaderboard global y rachas diarias
  - Analytics con programación paralela (MPI)
  - Modo Drag & Drop y Diagramas ER como formatos alternativos

  FLUJO DE UNA PETICIÓN HTTP:

  ┌──────────┐    HTTP Request     ┌──────────────────┐
  │ Frontend │ ──────────────────→ │ UsuarioController│
  │  (React) │                    │    @RestController│
  └──────────┘                    └────────┬─────────┘
                                          │
                    ┌─────────────────────▼─────────────────────┐
                    │         @Autowired UsuarioService          │
                    │  (Lógica de negocio, validaciones)        │
                    └─────────────────────┬─────────────────────┘
                                          │
                    ┌─────────────────────▼─────────────────────┐
                    │      UsuarioRepository extends JpaRepository│
                    │  (Interfaz: Spring genera las queries)     │
                    └─────────────────────┬─────────────────────┘
                                          │
                    ┌─────────────────────▼─────────────────────┐
                    │         PostgreSQL (lms_core / lms_sandbox)│
                    │    - usuarios, ejercicios_practicos, etc.  │
                    └────────────────────────────────────────────┘

  EJEMPLO CONCRETO - LOGIN:

  1. Frontend envía POST /api/usuarios/login { email, passwordHash }
  2. UsuarioController.loginUsuario() recibe la petición
  3. Llama a UsuarioService.iniciarSesion(email, password)
  4. UsuarioService usa UsuarioRepository.findByEmail(email)
  5. Spring Data JPA genera: SELECT * FROM lms_core.usuarios WHERE email = ?
  6. Se compara password_hash
  7. Si es correcto → JwtUtil.generarToken(idUsuario) → devuelve token
  8. Controller responde: { token: "eyJ...", user: { ... } }

  5. CONEXIÓN DE CLASES CON LA BASE DE DATOS
================================================================================

  DIAGRAMA DE CLASES Y SU CONEXIÓN A BD:

  ┌─────────────────────────────────────────────────────────────────────┐
  │                            MODELO (JPA)                            │
  │                                                                     │
  │  @Entity @Table(name="usuarios", schema="lms_core")                │
  │  class Usuario {                                                   │
  │    @Id @GeneratedValue(strategy=UUID)                              │
  │    private UUID idUsuario;       ← Mapeo a columna id_usuario      │
  │                                                                     │
  │    @Column(nullable=false, unique=true)                             │
  │    private String email;          ← Mapeo a columna email           │
  │    ...                                                             │
  │  }                                                                 │
  └───────────────────────────────────┬─────────────────────────────────┘
                                      │ JPA/Hibernate
                                      │ (ddl-auto=none → NO crea tablas)
                                      ▼
  ┌─────────────────────────────────────────────────────────────────────┐
  │                        REPOSITORY (Spring Data)                    │
  │                                                                     │
  │  @Repository                                                        │
  │  interface UsuarioRepository extends JpaRepository<Usuario, UUID> { │
  │    Optional<Usuario> findByEmail(String email);                     │
  │    // Spring traduce findByEmail →                                  │
  │    // "SELECT * FROM lms_core.usuarios WHERE email = ?"             │
  │  }                                                                 │
  └───────────────────────────────────┬─────────────────────────────────┘
                                      │ @Autowired
                                      ▼
  ┌─────────────────────────────────────────────────────────────────────┐
  │                          SERVICE                                   │
  │                                                                     │
  │  @Service                                                           │
  │  class UsuarioService {                                             │
  │    @Autowired private UsuarioRepository usuarioRepository;           │
  │                                                                     │
  │    public Usuario iniciarSesion(String email, String pass) {        │
  │      Optional<Usuario> opt = usuarioRepository.findByEmail(email);  │
  │      // ... validar contraseña ...                                 │
  │      return usuario;                                                │
  │    }                                                               │
  │  }                                                                 │
  └───────────────────────────────────┬─────────────────────────────────┘
                                      │ @Autowired
                                      ▼
  ┌─────────────────────────────────────────────────────────────────────┐
  │                        CONTROLLER                                  │
  │                                                                     │
  │  @RestController @RequestMapping("/api/usuarios")                   │
  │  class UsuarioController {                                         │
  │    @Autowired private UsuarioService usuarioService;                │
  │                                                                     │
  │    @PostMapping("/login")                                           │
  │    public ResponseEntity<?> loginUsuario(@RequestBody Usuario c) { │
  │      Usuario u = usuarioService.iniciarSesion(c.getEmail(), ...);   │
  │      return ResponseEntity.ok(u);                                   │
  │    }                                                               │
  │  }                                                                 │
  └─────────────────────────────────────────────────────────────────────┘

  EJERCICIO PRÁCTICO (Entidad y Repositorio):
  ┌─────────────────────────────────────────────────────────────────────┐
  │  @Entity @Table(name="ejercicios_practicos", schema="lms_core")    │
  │  class EjercicioPractico {                                         │
  │    @Id @GeneratedValue(strategy=IDENTITY)                           │
  │    private Integer idEjercicio;       ← PK autoincremental        │
  │    private Integer idModulo;           ← FK a tabla modulos        │
  │    private String enunciado;           ← Texto del ejercicio      │
  │    private String queryMaestra;         ← Respuesta correcta       │
  │    private String formato;              ← "editor", "drag_drop", "diagram" │
  │    private String configuracionExtra;   ← JSON con reglas adicionales │
  │  }                                                                 │
  │                                                                     │
  │  @Repository                                                        │
  │  interface EjercicioPracticoRepository extends JpaRepository<...> { │
  │    List<EjercicioPractico> findByIdModuloOrderByOrdenAsc(Integer);  │
  │  }                                                                 │
  └─────────────────────────────────────────────────────────────────────┘

  ACCESO DIRECTO CON JdbcTemplate (para consultas complejas):
  - UsuarioService, ModuloService, LeaderboardService usan @Autowired JdbcTemplate
  - Permite ejecutar SQL nativo: jdbcTemplate.queryForObject(sql, params)
  - Usado para: ranking, estadísticas de usuario, validación de módulos

  JWT UTIL (Generación y validación):

  @Component
  class JwtUtil {
    private static final Key SECRET_KEY = Keys.secretKeyFor(HS256);
    private static final long EXPIRATION_TIME = 86400000; // 24h

    // Crear token
    public String generarToken(String idUsuario) {
      return Jwts.builder()
        .setSubject(idUsuario)           // Guarda el UUID del usuario
        .setExpiration(new Date(System.currentTimeMillis() + EXPIRATION_TIME))
        .signWith(SECRET_KEY)            // Firma con llave secreta
        .compact();
    }

    // Validar token
    public boolean validarToken(String token) {
      try { getClaims(token); return true; }
      catch (Exception e) { return false; }
    }
  }

  SecurityConfig.java (Configuración de seguridad):

  @Configuration @EnableWebSecurity
  class SecurityConfig {
    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) {
      http
        .cors(cors -> cors.configurationSource(corsConfig())) // CORS
        .csrf(csrf -> csrf.disable())                         // Deshabilitar CSRF
        .authorizeHttpRequests(auth -> auth
          .requestMatchers("/api/usuarios/login", "/api/usuarios/registro").permitAll()
          .requestMatchers("/api/clawbot/**").permitAll()
          .anyRequest().authenticated()                        // Todo lo demás requiere JWT
        )
        .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class);
      return http.build();
    }

    // CORS: Permitir peticiones desde React (localhost:3000)
    @Bean
    CorsConfigurationSource corsConfigurationSource() {
      CorsConfiguration config = new CorsConfiguration();
      config.setAllowedOriginPatterns(Arrays.asList("*"));
      config.setAllowedMethods(Arrays.asList("GET","POST","PUT","DELETE","OPTIONS"));
      config.setAllowedHeaders(Arrays.asList("*"));
      config.setAllowCredentials(true);
      UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
      source.registerCorsConfiguration("/**", config);
      return source;
    }
  }

    const [token, setToken] = useState(localStorage.getItem('dagon_token'));
    const [user, setUser] = useState(null);

    const login = (token, user) => {
      localStorage.setItem('dagon_token', token);

      localStorage.removeItem('dagon_token');
      setToken(null);
      setUser(null);
    };

        {children}

 14. FLUJO COMPLETO DE UNA PETICIÓN
================================================================================

  CASO: Usuario resuelve un ejercicio SQL

  1. [Frontend] Usuario escribe SQL en Monaco Editor (ExercisePage.js)
     SELECT * FROM aventureros WHERE nivel > 10;

  2. [Frontend] Click en "Ejecutar" → validateExercise(exerciseId, query, levelId)
     POST http://localhost:8080/api/exercises/5/validate
     Headers: Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
     Body: { query: "SELECT * FROM aventureros WHERE nivel > 10;", usuarioId: "..." }

  3. [Backend] JwtAuthenticationFilter valida el token JWT
     - Extrae idUsuario del token
     - Setea Authentication en SecurityContext

  4. [Backend] NivelController.validarEjercicio(id, request)
     - Extrae queryUsuario y usuarioId del request body
     - Llama a ejercicioService.validarConsulta(id, queryUsuario, usuarioId)

  5. [Backend] EjercicioService.validarConsulta():
     a) SEGURIDAD: Verifica que no sea DROP DATABASE, TRUNCATE, etc.
     b) Obtiene el ejercicio de la BD: repository.findById(ejercicioId)
     c) Si es el MÓDULO 15 (Transacciones):
        - Trocea la query y genera `transactionSimulation` (simulando concurrencia A/B).
        - Empaqueta el estado inicial, final y los eventos simulados en la respuesta.
     d) Lee queryMaestra: "SELECT * FROM aventureros WHERE nivel > 5;"
     e) Ejecuta queryMaestra en sandbox (con rollback) → datosMaestros
     f) Ejecuta queryUsuario en sandbox (persistente) → datosAlumno
     g) Compara resultados ignorando columnas id/id_
     h) Si es correcto:
        - Inserta en lms_core.intentos (registro de intento)
        - Actualiza racha diaria: usuarioService.registrarPracticaDiaria()
        - Responde: { success: true, xp_gained: 50, transactionSimulation: [...] }
     i) Si es incorrecto:
        - Inserta intento con es_correcto = false
        - Responde: { success: false, message: "Los datos no coinciden",
                      queryMaestra, queryAlumno, transactionSimulation: [...] }

  6. [Frontend] ExercisePage.js recibe la respuesta
     - Si success: true → Muestra animación de éxito, suma XP, avanza
     - Si success: false → Muestra error, ofrece ayuda de Clawbot

  7. [Frontend] Si el usuario pide ayuda → Clawbot
     POST /api/clawbot/analyze
     Body: { descripcion, queryMaestra, queryAlumno, errorDb, intentos }
     → ClawbotService → Gemini API → Respuesta pedagógica socrática

================================================================================
1. RESUMEN EJECUTIVO
================================================================================

Dagon es una plataforma LMS gamificada para enseñar SQL/PostgreSQL a estudiantes
principiantes. El objetivo no es solo mostrar ejercicios, sino crear una experiencia
educativa completa:

  - El alumno entra a una interfaz React protegida por autenticación.
  - Ve cursos, módulos, progreso, ranking y recompensas.
  - Antes de practicar, recibe cinemáticas educativas por módulo.
  - Practica con formatos graduales: drag and drop, editor SQL, diagramas MER,
    DDL, DML, transacciones y ejercicios rápidos.
  - El backend valida sus respuestas en PostgreSQL.
  - Cada alumno tiene su propio sandbox: un esquema aislado en la BD.
  - Los intentos se guardan y alimentan XP, ranking, rachas y certificados.
  - Clawbot da retroalimentación socrática si el alumno falla.
  - Un microservicio MPI procesa analytics del ranking en paralelo.

Idea central para defender:

  "Dagon enseña SQL ejecutando SQL real, pero lo hace de forma segura porque cada
   usuario practica dentro de su propio esquema sandbox. La arquitectura separa
   frontend, backend, base de datos, IA y analytics, y usa patrones de diseño para
   mantener responsabilidades claras."

2. EXPLICACIÓN CORTA PARA ABRIR LA DEFENSA

Puedes decir esto al inicio:

  "Dagon es un LMS gamificado para aprender SQL. El frontend está hecho en React
   y muestra login, dashboard, módulos, cinemáticas, ejercicios, ranking, perfil,
   certificados y Clawbot. El backend está hecho en Spring Boot y expone endpoints
   REST, seguridad JWT, servicios de negocio, validación SQL y conexión con
   PostgreSQL. La base de datos tiene un esquema principal llamado lms_core, un
   template de práctica llamado lms_sandbox_template y un esquema por usuario con

   PostgreSQL crea automáticamente su sandbox clonando el template. Así cada alumno
   puede hacer SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER o transacciones sin
   dañar el trabajo de otros. Además, el ranking se calcula con una vista SQL, el
   tutor Clawbot ayuda con pistas socráticas y el servicio MPI analiza métricas en
   paralelo usando scatter, gather y reduce."

--------------------------------------------------------------------------------
5.1 MVC / Arquitectura por capas
--------------------------------------------------------------------------------

Dónde está:
  - View: React, pages y components.
  - Controller: clases @RestController.
  - Model: entidades JPA y tablas PostgreSQL.
  - Service: lógica de negocio.
  - Repository: acceso a datos.

Por qué:
  - Separa responsabilidades.
  - Permite explicar el proyecto por capas.
  - Evita que React conozca SQL interno.
  - Evita que los controladores tengan toda la lógica.

Ejemplo:

  ExercisePage.js
    -> NivelController
      -> EjercicioService
        -> EjercicioPracticoRepository / JdbcTemplate
          -> PostgreSQL

--------------------------------------------------------------------------------
5.2 Repository
--------------------------------------------------------------------------------

Dónde está:
  - UsuarioRepository extends JpaRepository<Usuario, UUID>
  - EjercicioPracticoRepository extends JpaRepository<EjercicioPractico, Integer>

Por qué:
  - Abstrae CRUD.
  - Spring genera consultas por convención.
  - Reduce SQL repetitivo.

Ejemplos:
  - findByEmail(String email)
  - findByIdModuloOrderByOrdenAsc(Integer idModulo)

Cómo explicarlo:
  "El repository es una interfaz. Yo declaro lo que necesito y Spring Data genera
   la implementación, conectándola con Hibernate y PostgreSQL."

--------------------------------------------------------------------------------
5.3 DTO
--------------------------------------------------------------------------------

Dónde está:
  - EjercicioDTO
  - NivelDTO

Por qué:
  - La entidad de BD no siempre es lo mismo que necesita el frontend.
  - El DTO evita exponer campos internos.
  - Permite transformar un ejercicio SQL en una experiencia educativa.

Ejemplo:
  - En BD existe query_maestra.
  - En frontend se envía title, description, type, hint y wordBank.

--------------------------------------------------------------------------------
5.4 Dependency Injection / IoC
--------------------------------------------------------------------------------

Dónde está:
  - @Autowired
  - @Service
  - @RestController
  - @Component
  - @Configuration

Por qué:
  - Spring crea y conecta objetos.
  - Evita crear dependencias manualmente.
  - Facilita cambiar implementaciones.

Ejemplo:
  @Autowired private EjercicioService ejercicioService;

--------------------------------------------------------------------------------
5.5 Filter Chain / Chain of Responsibility
--------------------------------------------------------------------------------

Dónde está:
  - SecurityConfig
  - JwtAuthenticationFilter

Por qué:
  - Cada petición pasa por filtros.
  - El filtro JWT valida token antes del controller.
  - Centraliza seguridad.

Flujo:
  Request HTTP
    -> CORS
    -> JwtAuthenticationFilter
    -> Controller

--------------------------------------------------------------------------------
5.6 Guard / Protected Route
--------------------------------------------------------------------------------

Dónde está:

Por qué:
  - Protege rutas frontend.
  - Si no hay token, redirige al login.
  - Complementa la seguridad del backend.

5.7 Context Provider
--------------------------------------------------------------------------------

Dónde está:

  - ThemeContext

Por qué:
  - Comparte usuario, token, login/logout y tema visual.

5.8 Singleton / Facade para sonido

5.9 Adapter / Proxy para servicios externos

Dónde está:

12. SANDBOX SQL POR USUARIO
================================================================================

Problema:
  Un alumno puede ejecutar UPDATE, DELETE, INSERT, CREATE o ALTER.
  Si todos usaran las mismas tablas, romperían los datos de otros alumnos.

Solución:
  Cada usuario tiene un esquema propio.

Ejemplo:
  Usuario con id e1eeb361-...
  usa:
    sandbox_usuario_e1eeb361-...

El alumno escribe:
  SELECT * FROM aventureros;

El backend ejecuta:
  SET search_path TO "sandbox_usuario_<uuid>";
  SELECT * FROM aventureros;

Resultado:
  La consulta ocurre dentro de su propio sandbox.

================================================================================
20. PREGUNTAS PROBABLES Y RESPUESTAS
================================================================================

P: ¿Cuál es el patrón principal?
R: Arquitectura por capas/MVC: React como vista, controllers REST como entrada,
services como lógica, repositories/JdbcTemplate como persistencia y PostgreSQL
como modelo de datos.

P: ¿Por qué Repository?
R: Para abstraer CRUD y consultas comunes. Spring Data genera implementaciones.

P: ¿Por qué DTO?
R: Porque lo que guarda la BD no siempre es lo que necesita la UI. El DTO prepara
datos para experiencias educativas como drag and drop o diagramas.

P: ¿Cómo evitas que un alumno dañe datos de otro?
R: Cada usuario tiene un esquema propio `sandbox_usuario_<uuid>` y el backend usa
`SET search_path` para ejecutar ahí.

P: ¿Cómo se crea el sandbox?
R: Con un trigger AFTER INSERT sobre usuarios que ejecuta `fn_crear_multiverso()`.

P: ¿Qué patrón es ese trigger?
R: Observer a nivel BD. Observa un evento y reacciona automáticamente.

P: ¿Qué patrón es el template de sandbox?
R: Prototype/Factory. `lms_sandbox_template` es el prototipo y la función crea
una copia por usuario.

P: ¿Cómo funciona el ranking?
R: Con `v_ranking_alumnos`, que calcula XP desde intentos correctos.

P: ¿Cómo funciona Clawbot?
R: El backend envía contexto del error a un proveedor IA o usa fallback, siempre
con reglas socráticas para no revelar la solución.

P: ¿Dónde entra MPI?
R: En analytics del ranking. Spring llama a Flask, Flask lanza `mpirun`, MPI divide
usuarios entre ranks y consolida métricas.

P: ¿Qué harías antes de producción?
R: Cerrar CORS, proteger rutas sensibles, sanitizar dump, separar SQL y refactorizar
validadores por tipo de ejercicio.

CIERRE SUGERIDO
================================================================================

Frase final:

  "Dagon no es solo una interfaz para practicar SQL. Es una arquitectura educativa
   completa: React guía al alumno, Spring Boot protege y coordina la lógica,
   PostgreSQL crea sandboxes y calcula progreso, Clawbot da retroalimentación
   y MPI agrega análisis paralelo. Los patrones de diseño permiten separar
   responsabilidades, aislar usuarios, escalar la lógica educativa y explicar el
   sistema por capas de forma mantenible."
