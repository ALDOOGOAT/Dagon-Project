================================================================================
ANÁLISIS TÉCNICO: MÓDULO 15 (TRANSACCIONES) Y PARALELISMO EN DAGON
================================================================================

Este documento detalla el funcionamiento interno del Módulo 15 (Orden 11),
enfocado en transacciones de PostgreSQL (BEGIN, COMMIT, ROLLBACK, SAVEPOINT) y
cómo interactúa con conceptos de paralelismo y sistemas distribuidos.

--------------------------------------------------------------------------------
1. ¿ES PARALELISMO REAL? (LO QUE ES Y LO QUE NO ES)
--------------------------------------------------------------------------------
En el contexto del Módulo 15, NO estamos hablando de paralelismo de hardware
(cálculo distribuido en múltiples núcleos). Lo que se implementa aquí es una
SIMULACIÓN PEDAGÓGICA DE CONCURRENCIA.

- LO QUE SÍ ES: Una representación visual y lógica del principio de "Aislamiento"
  (Isolation en las propiedades ACID), mostrando cómo múltiples sesiones de base
  de datos interactúan de manera concurrente (Sesión A y Sesión B).
- LO QUE NO ES: No ejecuta hilos paralelos reales de procesamiento de datos en
  el backend para resolver el ejercicio en el sentido estricto de MPI/Hilos.

NOTA SOBRE PARALELISMO DISTRIBUIDO (MPI):
Si en la materia de Programación Distribuida y Paralela buscan el uso estricto
de paralelismo de hardware, el proyecto Dagon lo implementa en el servicio
analítico (`mpi_service`). Allí se usa Python con `mpi4py` (Open MPI) para
dividir el cálculo del ranking de usuarios en múltiples procesos paralelos
físicos (Ranks), orquestados a través de `AnalyticsController.java`.

--------------------------------------------------------------------------------
2. CLASES Y MÉTODOS INVOLUCRADOS EN EL BACKEND
--------------------------------------------------------------------------------
La lógica detrás de la validación transaccional se orquesta combinando el
Backend en Java y la base de datos:

* Archivos DB:
  - `para dilman/transaccion.sql` (y BD): Inyecta la metadata `configuracion_extra`
    (`"sesiones_paralelas": true`) en la tabla `ejercicios_practicos` para el
    Módulo 15.

* Clases Backend Java (`backend/src/main/java/com/dagon/backend/service/EjercicioService.java`):
  El motor principal de evaluación utiliza métodos específicos:
  - `esMisionTransaccional(ejercicio)`: Detecta mediante JSON si el ejercicio
    actual es un laboratorio transaccional.
  - `evaluarQuery(...)`: Orquesta la evaluación. Determina si la consulta es de
    modificación e inicia el flujo.
  - `construirSimulacionTransaccional()`: Parsea paso a paso la cadena de SQL del
    usuario y genera un árbol de eventos simulando lo que ocurre en Sesión A y B.
  - `extraerNombreTablaTransaccional()`: Usa Expresiones Regulares (Regex) en
    Java para saber exactamente a qué tabla se le hizo INSERT, UPDATE o DELETE.
  - `construirHintVisibilidad()`: Analiza el contexto para dictaminar si los datos
    son visibles para ambas sesiones (COMMIT completado) o si están retenidos
    en aislamiento (transacción abierta no confirmada).

--------------------------------------------------------------------------------
3. CÓMO EVALÚA AL USUARIO Y QUÉ QUERYS MANDA A LA BD
--------------------------------------------------------------------------------
Cuando el usuario envía su código SQL (ej: "BEGIN; INSERT...; COMMIT;") desde
la consola del frontend, el proceso es muy dinámico:

1. Detección e Identificación: El backend intercepta la petición y mediante Regex
   identifica la tabla afectada (ej. "aventureros").
2. Snapshot "Antes": El backend manda una consulta a la BD (esquema sandbox aislado
   del usuario) para fotografiar el estado inicial de la tabla objetivo:
   -> `SELECT * FROM "<tabla_afectada>" LIMIT 20;`
3. Ejecución Aislada: El backend ejecuta la totalidad de la transacción
   enviada por el usuario en su respectivo entorno (para evaluar sintaxis y
   generar los cambios en el disco de PostgreSQL de forma segura).
4. Snapshot "Después": El backend ejecuta otra vez un select general para capturar
   el resultado de las modificaciones:
   -> `SELECT * FROM "<tabla_afectada>" LIMIT 20;`
5. Troceo y Simulación: En lugar de usar una "respuesta correcta preestablecida",
   se invoca a `construirSimulacionTransaccional`. Se lee el texto del usuario
   y se divide en eventos lógicos (ej: Evento 1 -> BEGIN; Evento 2 -> INSERT;
   Evento 3 -> COMMIT), evaluando la propiedad de aislamiento en cada paso.
6. Retorno: Empaqueta los snapshots ("beforeData", "afterData") junto con el
   arreglo de simulación ("transactionSimulation") y lo devuelve.

--------------------------------------------------------------------------------
4. DIAGRAMA DE ESTRUCTURA Y FUNCIONAMIENTO
--------------------------------------------------------------------------------

[Usuario (Frontend)] --escribe SQL--> "BEGIN; INSERT...; COMMIT;"
        |
        v
[Controlador REST (API)] ---> Recibe Payload de validación
        |
        v
[EjercicioService (Backend)]
        |
        +---> 1. Verificación de Metadatos: ¿Módulo 15? ¿sesiones_paralelas = true?
        |
        +---> 2. Obtiene Tabla Afectada (Regex Engine)
        |
        +---> 3. PostgreSQL Sandbox DB: `SELECT * FROM <tabla> LIMIT 20` (INICIAL)
        |
        +---> 4. PostgreSQL Sandbox DB: Ejecuta "BEGIN; INSERT...; COMMIT;"
        |
        +---> 5. PostgreSQL Sandbox DB: `SELECT * FROM <tabla> LIMIT 20` (FINAL)
        |
        +---> 6. Lógica de Aislamiento: `construirSimulacionTransaccional()`
                 - Detecta keywords (BEGIN, SAVEPOINT, ROLLBACK, COMMIT)
                 - Crea eventos temporales pseudo-paralelos
                 - Asigna reglas de visibilidad (Concurrencia)
        |
        v
[JSON Response] ---> { 
                         transactionSimulation: [...eventos_explicados], 
                         beforeData: [...], 
                         afterData: [...] 
                     }
        |
        v
[Frontend (React)] ---> Renderiza paneles en pantalla dividida ("Sesión A" y "Sesión B")
                        mostrando en tiempo real cómo los datos aparecían o estaban
                        ocultos para las distintas sesiones concurrentes.

--------------------------------------------------------------------------------
RESUMEN Y CONTEXTO ACADÉMICO
--------------------------------------------------------------------------------
En el marco de la materia, este módulo no emplea hilos concurrentes del CPU 
(para ello ver la arquitectura `mpi_service`), sino que enseña los **conceptos 
teóricos fundamentales de la programación paralela y concurrente en bases de datos**, 
como lo son el **aislamiento** (isolation), la visibilidad de datos sucios (dirty reads) 
y el control de transacciones, esenciales para cualquier sistema distribuido seguro.
